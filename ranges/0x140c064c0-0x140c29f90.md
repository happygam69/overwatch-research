# Pass 69 — chunks `0620`–`0628`, `.text` `0x140c064c0`–`0x140c29f90`

Pass 68 stopped inside the JSON-Schema keyword accessors and its watch list named the
evaluator half as the first item. It is there — the `$ref` resolver, the JSON-pointer
parser and the string/array validator arms all sit in chunk 0620's first 40 KB, and the
schema engine turns out to have a named client (`Bleep Client Config`). After that the
range changes strata twice:

1. **`0x140c064c0`–`0x140c0bb30` — the JSON-Schema evaluator + `$ref` + a 0x828-B UI
   panel.** The 3 remaining keyword accessors, the `$ref` resolver (`FUN_140c06c00`),
   the JSON-pointer parser (`FUN_140c08300`), the string-length/pattern arms
   (`FUN_140c09aa0`/`0x140c09c10`), the numeric bound emitters, and `FUN_140c08640` —
   the **Bleep client-config validator**, which carries a hardcoded draft-04 schema
   (`"title": "Bleep Client Config"`) as an inline string. Behind it a 0x828-B widget
   (ctor `FUN_140c0ac80`, dtor `FUN_140c0b2d0`, teardown `FUN_140c0b420`).
2. **`0x140c0bb70`–`0x140c15920` — the "Jam" session/connection client.** A separate
   library: message kinds `0xd548`–`0xd54b`, the literal log line
   `"Unhandled JamMessage, unable to dispatch"`, a session state machine
   (`0`→`7`), an HMAC-style challenge/response, and a 4-state async *load* machine.
   `CityHash64WithSeed` is called by name here.
3. **`0x140c15d20`–`0x140c29f90` — the persistent value-trie "record store", the
   broadphase query belt, and the scene/mesh build masters.** Two hash ladders are
   confirmed verbatim, the `0x1e10` id→record map is mapped field by field, and the
   compressed-bitset trie (`+0x110` bitsets / `+0x130` rank bytes) is walked in eight
   different functions. Five of this pass's largest bodies are window hosts that
   re-emit that same construct.

Zero registrations, zero records: **69 consecutive consumer-only passes**. 308 functions
for 1,122,128 B of post-strip text (the *sum* of declared `size=` is only 137,299 B —
this is the most window-dominated range of the run).

**The `$ref` resolver, `FUN_140c06c00`** (evidence). Two arms, split on whether the
reference text starts with `'#'`:

- external reference: `(*param_1)[0x08](param_1, text, len)` is a caller-supplied vtable
  hook returning a definition node, then `FUN_140c068e0` scans the 0x48-stride node array
  at `+0x38`/`+0x40` for a key match (compares `+0x30` int, `+0x20` u64 length, then
  `memcmp` over 0x10-stride `{char* ptr, u32 len, u32 pad}` segments). Hit → the node's
  `+0x38` value, emitted through `FUN_140bfe750(node, value, target, 0)`.
- internal reference: `FUN_140c08300(text, len)` splits the JSON pointer into segments,
  then walks the schema value with `FUN_140bf9510` — key lookup for `tag&7 == 3`
  (array-of-0x20), index lookup for `tag&7 == 4` (array-of-0x10, `u14 == 0xffffffff` or

  `FUN_140bfb8c0`. On any failure it pads `param_1[0xf] - param_1[0xe] < 0x78` first,

**The JSON-pointer parser, `FUN_140c08300`** (evidence). Returns a status at
`param_1+6`: `0` ok, `1` text after `'#'` does not start with `'/'`, `2` bad `~` escape

`-._~`, digits, letters, and the unreserved punctuation). Segment rows are 0x10 B:
`{char* text, u32 len, int index}` where `index = -1` unless the segment is all digits
and fits a u32 (`uVar13*10 + d - 0x30` with a wrap check). The array is
`param_1[3]`, cursor `param_1[2]`, count `param_1[4]` = the number of `'/'` in the
input, allocated as `len + count*0x10`.
